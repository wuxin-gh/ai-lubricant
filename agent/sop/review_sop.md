# Review SOP

对抗性代码评审。用户说 "review" / "评审" / "看看这段代码有没有问题" 时启用。

## 三条铁律

1. **只读评审**。评审就是评审：禁止在评审过程中改源文件、用 `file_write`/`file_patch`
   改业务代码、或在报告里写「我接下来去修一下」。要修是下一个任务，由用户决定。
2. **先质疑路子，再找 bug**。第一个问题是「这条路本身对不对」，第二个才是「实现有没有
   bug」。只找语法级缺陷的评审没有价值。
3. **报告输出完即结束**。不复述用户目标、不做元评论、不承诺后续动作。

## 流程

1. `file_read("memory/sop/code_review_principles.md")` —— 每条 finding 必须能映射到其中
   一条原则。没有对应原则的「发现」通常是个人口味。
2. **锁定范围**：用户点名了文件就审那些；只说了任务范围就用 `code_run` 跑
   `git status -s` + `git diff --stat HEAD` + `git diff HEAD`；空或模糊就默认审未提交改动。
   非 git 仓库直接要路径，本轮结束。**先把范围列给用户确认再开始读**。
3. **逐文件 `file_read`**。超过 800 行分段读。先看 diff 涉及的行，再看上下文和调用方——
   只读 diff 会漏掉「改动本身没错，但破坏了调用方契约」这类问题。
4. **回答 Q1-Q4**（对抗性 framing，缺一不可）：
   - Q1 这是对的方法吗？有没有更简单/更标准/更安全的路径？
   - Q2 有哪些隐藏依赖会失效？OS / shell / 网络 / 并发 / 第三方 API / 编码。
   - Q3 什么边缘或敌意输入能打破它？空值、UTF-8、Windows 路径、超长输入、过期凭据。
   - Q4 故障可观测、可恢复吗？只看日志能定位吗？不动手能恢复吗？
5. **列 findings**，按 P0→P3 排序，过完下面的防误报八问再提交。

## Severity 与 Verdict

| 级别 | 定义 | 例子 |
|---|---|---|
| P0 | 阻塞：破坏正确性 / 丢数据 / 安全漏洞 / 不可逆故障 | 路径穿越、SQL 注入、密钥落日志、竞态破坏数据 |
| P1 | 高危：契约破坏 / 用户可见错误，但不会立即崩 | 错误只打印不抛、没设超时、schema 不一致 |
| P2 | 维护性：可读性 / 命名 / 测试空缺 | 函数过长、重复逻辑、注释与代码不符 |
| P3 | 风格 / 微优化 | 命名小调、常量提取 |

**Verdict**：任一 P0 → `FAIL`；无 P0 但有 P1 → `CONDITIONAL`；仅 P2/P3 或零 finding → `PASS`。
这条是硬规则——报了 P0 却给 PASS 是评审本身失效。

## 防误报八问（成本低到高，任一答 No 就删掉这条 finding）

1. **具体可修**？能写出确定的修法，不是「建议关注一下」。
2. **本次改动引入或放大的**？既有问题不算这次的账，除非改动把它暴露成了可触发路径。
3. **不是作者刻意取舍**？看得出是权衡（有注释、有对称处理）就不要当缺陷报。
4. **可证明受影响，不是推测**？跨文件影响必须指出调用栈，说不出就是猜。
5. **有证据锚点**？行号、代码片段、复现步骤，至少一项。
6. **不依赖未明说的假设**？「应该用 X 模式」不是缺陷。
7. **作者知道后大概会修**？会说「这不是问题」的，就别报。
8. **影响够大且严谨度匹配**？一次性脚本不按生产库的标准审。

## 措辞规范

- **先说为什么**：第一句给原因，不是给现象。
- **严重度准确**：不要把 P2 写得像 P0，那会让整份报告失信。
- **简洁**：evidence / impact / fix 各不超过一段；代码片段 ≤ 5 行，超了用 `file:N-M` 引用。
- **触发条件显式**：impact 第一句必须带场景、输入或环境。
- **零奉承**：不写「整体不错，但是……」。直陈事实，不带情绪。

## 输出格式

```
## Scope
<一行一个文件>

## Verdict
PASS / CONDITIONAL / FAIL

## Summary
3-6 行：整体印象 + 最重要的 1-2 个风险。

## Design Challenge
- Q1 是不是对的方法：<证据>
- Q2 隐藏依赖：<证据>
- Q3 边缘/敌意输入：<证据>
- Q4 故障可观测：<证据>

## Findings（P0 → P3）
- **[P0] file:line-line** 动词开头的标题，第一句给原因
  - Evidence: 代码片段或 file:N-M
  - Impact: 触发场景 + 后果
  - Fix: 可直接照做的修法
  - Principle: 对应 code_review_principles 第 N 条

## Cross-file notes
跨文件耦合 / 命名一致性 / 状态机 / 并发。无则 (none)。

## Regression tests
3-5 条具体测试点（输入 / 预期 / 边界）。
```
